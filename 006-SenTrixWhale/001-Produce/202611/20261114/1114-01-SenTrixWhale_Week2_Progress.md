# SenTrixWhale · 工程鲸 设计与实测总览

> 四份材料合并：设计概览 / EXIF 现状 / 存图策略 / PA 的 EXIF 抢救调研。
> 生成于 2026-11-12，核对环境：90（Mac mini M4）+ 224（NapCat 临时桥，本周缓兵之计）。

---

## 一、一句话

**给家庭记忆系统装上一个"人人可用"的对话入口：发一张照片、说一句话，它就记住；问一句，它答得出是哪天、在哪、在干什么。**

---

## 二、要解决什么

B 站上的 AI 人格角色很火，但都有同一个短板：**聊完即忘**。

| 症状 | 后果 |
|---|---|
| 上下文到上限就清零 | 昨天聊的今天不认 |
| 沉淀不下来 | 没有可检索的长期记忆 |
| 更无法复现 | 它说"我记得"，你拿不出证据让它调出来 |

两块拼图：

- **记忆内核**：`sentrix-home-web-2.0` —— VLM → 多通道索引 → 检索 → QA 评测
- **对话套件**：QQ 交互层 —— 护栏、日记、识图、防幻觉，已有真机验证

拼起来就是工程鲸：**记忆有堤坝，交互有温度。**

## 四、两个数据流

### 4.1 存

```
用户发图 → 她追问「什么时候、在哪儿拍的」
        → 用户答「深圳南山 2023年4月29日」
        → 解析成 {相册路径: 广东/深圳/南山, 时间: 2023-04-29}
        → 归档到 media/photos/广东/深圳/南山/
        → 把时间和 GPS 写进 EXIF
        → 上传 SHW，scope_id = 相册路径
        → 回「收好了 🐳 收进《广东/深圳/南山》，记作 2023-04-29」
```

### 4.2 取

```
用户问「2023年4月」→ 解析出时间区间
                  → SHW 检索（时间窗 + 语义）
                  → 取时间线事件摘要（"石家庄裕华公园吃草莓"）
                  → Qwen3.5 组织成一句人话
```

**关键取舍**：向量检索只返回文件名和时间，说不了话；真正能"说事"的是时间线里的**事件摘要**。

## 五、相册与时间

### 5.1 目录结构

```
media/photos/
├── 全球/<洲>/<国>/<市>/        德国柏林、日本东京
├── 全国/<省>/<市>/             陕西西安、福建厦门
└── 广东/<市>/<区>/             深圳南山、广州天河   ← 用户注册地，可换
```

| 分支 | 层级 | 做不做区 |
|---|---|---|
| 全球 | 洲 / 国 / 市 | 不做 |
| 全国 | 省 / 市 | 不做 |
| 本地省 | 市 / 区 | **做** |

**为什么本地省做到区、外地不做**：不是精度偏好，是能力边界。深圳的"南山""福田"天天在，张口就来；去趟西安没人记得住"碑林区"，做了也空着。

### 5.2 直辖市

省=市时**只写一次**：

```
全国/上海               ✅
全国/上海/上海           ❌ 同一个名字当两级用
全国/上海/浦东新区        ✅ 将来做区级时，区直接挂在市下面
```

三级会让前缀检索把同一座城市劈成两种形状，目录树也会出现同名父子。

### 5.3 地名从哪来

STW 仓库里带了一份自己的地理库（`data/geo/`，共 54 KB）：

| 文件 | 内容 | 大小 |
|---|---|---|
| `cn.json` | 35 省 / 348 地级市 / **2869 区县** | 35 KB |
| `world.json` | 46 国 / 洲 / 183 城市与州（含反向索引） | 19 KB |

国内数据从 SHW 的 PyGeoCN（天地图边界）**提取纯名字**，16 MB 的边界坐标全部剔掉，只留三级名称。
所以 SHW 与 STW 用的是同一份行政边界，**不会出现"她说的区和你文件夹里的区不一致"**。

解析用 `media/geo_lookup.js`，两条经验写进了代码：

1. **单字地名一律不要**——很多区去掉"区"只剩一个字（"东""南""西"），
   一句"**日本东京**"里的"东"会被当成四川攀枝花的**东区**，照片就存到攀枝花去了
2. **同名按级别挑**——"西安"既是陕西的市，也是吉林辽源的区。
   规则是「有市命中时，先看有没有属于该市的区」：「深圳南山」到区，「西安」不会被「西安区」抢走

另有直筒子市（东莞、中山不设区），其"区"名与市同名，路径做去重。

### 5.4 小鲸鱼能查地理

`geo_lookup.ask()` 让 bridge **在本地先判一次**，命中就直接回，不烧模型：

```
你：慕尼黑在哪个国家    她：慕尼黑在德国（欧洲）
你：杭州有哪些区        她：杭州下辖 13 个区县：上城、临安、临平、余杭、富阳…
```

不让 4B 模型自己调工具——它的 function calling 靠不住，本地查又快又准，还省一次推理。

### 5.5 时间写法（全部支持）

| 用户可能说 | 解析成 | 精度 |
|---|---|---|
| `20230429` / `230429` | 2023-04-29 | day |
| `2023-04-29` / `2023/4/29` | 2023-04-29 | day |
| `2023年4月29日` / `23年4月29日` | 2023-04-29 | day |
| `去年3月15日` / `前年12月1日` | 2025-03-15 / 2024-12-01 | day |
| `3年前 5月20日` | 2023-05-20 | day |
| `5个月前的12日` | 2026-06-12 | day |
| `10天前` / `昨天` / `前天` | 相对今天 | day |
| `4月29日` | 今年 04-29 | day |
| `2023年4月` | 2023-04-01 | **month** |
| `2023年` | 2023-01-01 | **year** |
| 公历节日：元旦 / 圣诞 / 国庆 / 劳动节等 11 个 | 对应日期 | day |
| 附加时刻 `16:50` / `23点04分` | 覆盖默认 12:00 | — |

**歧义规则**：6/8 位纯数字优先当日期（`230429`），4 位纯数字优先当时刻（`1650`）。

### 5.6 三条铁律

1. **词典只解决"归位"，不解决"能不能存"** —— 词典没有的地名（波尔图）照样建 `全球/未归类/波尔图`，绝不拒绝
2. **说得出区就记区，说不出就停在市，不逼问**
3. **时间解析不出来就不写，不猜"今天"** —— 猜出来的时间会让"没存到"变成"存错了地方"

## 六、存图策略：按入口分流

### 6.1 两个入口，两套策略

| 入口 | 归谁 | 场景 | 无信息的图 |
|---|---|---|---|
| SHW 网页 / 客户端导入 | **SHW 产品** | 迁移历史照片，几千张 | 跳过，不入库（组会决定） |
| **QQ 聊天** | **STW** | 一张张发，家庭日常 | **追问** |

**组长的意见没错，但说的是另一个入口。** QQ 入口不存在批量场景——普通家庭部署不会一次导几千张，照片就在手机里，一张张发。

所以 STW 的产品代码里**不需要"批量跳过"逻辑**。`import_testframes.js` 是给演示铺数据的一次性工具，不是产品路径。

### 6.2 QQ 入口的话术（已实现）

```
收到图（什么都没有）
  → 这张照片收到啦 🐳 要不要跟我说说它？什么时候、在哪儿拍的呀？

只说了时间
  → 地方记下了 🐳 还差个日子——大概什么时候拍的？

只说了地点
  → 啥时候拍的记下了 🐳 还差个地方——在哪儿拍的呀？

说了半句听不懂
  → 没关系，慢慢想～ 像这样说一句就好：「深圳南山 2023年4月29日」

三轮还说不清
  → 那这张我先替你放着，不着急 🐳 哪天想起来了，把图再发我一次，
    或者跟我说一句「收回刚才那张」，我再给它安家。

存好了
  → 收好了 🐳 收进《广东/深圳》，记作 2025-05-03。
```

三个设计意图：**不催**（不倒数）、**拒收不赶人**（留两条后路）、**存好要复述**（让她自己核对）。

### 6.3 为什么值得做

家人鲸在 Ubuntu 上陪跑一段时间，最直接的感受是：**它不是一个查询接口，是个有温度的家庭助手。**

技术上，追问会多一轮交互、多一次模型调用；但这类产品里，**"她愿意多问一句"本身就是价值**——用户发照片是想被回应，不是想填表单。

## 七、EXIF 现状（实测与结论）

### 7.1 结论

| 项 | 状态 | 条件 |
|---|---|---|
| **拍摄时间** | ✅ 可自动 | 原相机拍摄 + 勾选原图 |
| **地理坐标** | ❌ **不可得** | 华为实测：源头不写 |
| 相机型号 | ✅ 可自动 | 同时间 |

> **【2026-11-12 定案】** 四张实拍、两条通道（图片原图 / QQ 文件）、手机重启前后，
> 华为 nova 13 原相机写出的 GPS 段永远是空壳 `(nan, nan, nan)`。
> QQ 文件通道传过来的字节数与手机端完全一致（7,478,692 / 2,205,230），
> 证明**源头即空**，与传输链路无关。

### 7.2 按拍摄方式实测

| 拍摄方式 | 时间 | GPS | 备注 |
|---|---|---|---|
| 华为原相机 | ✅ 精确到秒 | ❌ 空壳 | 勾原图才有时间 |
| **QQ 内置相机** | ❌ **完全没有** | ❌ | EXIF 整段为空 `keys: []` |
| 微信内置相机 | 未测 | ❌ | 大概率同 QQ |

**修正口径**：时间"可自动"的前提是**原相机拍摄 + 勾选原图**；QQ/微信内置相机拍的照片连时间都没有。
所以追问流程是**默认两项都问，能省则省**。

### 7.3 机制：为什么会丢（PA 调研）

- QQ 一条图片消息在服务端生成多档：**原图 / 大图 / 缩略图**
- 不勾原图：走压缩重编码，元数据被剥
- **勾原图：服务端保留原图资源，但协议端上报的 `url` 默认指向大图档**；原图要用 `file`/`md5` 走专门接口才能拿到

实测证据（同一张图）：

| 取哪个档 | 体积 | 尺寸 | DateTime | GPS |
|---|---|---|---|---|
| 大图档（`url`） | 479 KB | 1080×1440 | ❌（程序补写的占位） | ❌ |
| 原图档（`Ori/`） | 1,068,148 B | 1080×1440 | ✅ 18:17:11 | ❌ |
| 文件通道（不转码） | 7,478,692 B | 4096×3072 | ✅ | ❌ 空壳 |

**结论**：协议端只是搬运工。手机没写进 GPS，换 NapCat / Lagrange / SnowLuma / icqq 都一样。

### 7.4 已经跑通的那条路（带 GPS 的图）

用 `00TestFrames/frame0110003.jpg`（EXIF: `2025:05:03 10:21:00` + GPS `22.550012,114.092608`）模拟一条 QQ 图片消息：

```
[EXIF] 自动识别 广东/深圳 2025-5-3 (22.550012,114.092608)
她回： 收好了 🐳 收进《广东/深圳》，记作 2025-05-03。

落盘: media/photos/广东/深圳/2025-05-03_102100_95662b79.jpg
SHW : captured_at = 2025-05-03T10:21:00
      gps         = 22.550012, 114.092608
```

**全程没有问用户一句话。** 这是苹果那种"照片自带 GPS"的设备会走的路径，代码级已验证，不是"应该能行"。

### 7.5 修复的三个坑（都是自己写坏的）

1. **`exif-reader` 对华为段抛 `Invalid EXIF data`** —— 传了整张 JPEG，它要的是 APP1 段，一直被 catch 吞掉 → 改用 PIL
2. **字段名不匹配** —— python 输出 `lat`/`lon`，JS 读 `latitude`/`longitude`
3. **`cr.ok` 判错** —— `resolveAlbum('深圳')` 返回 `ok:false`（要求文本里有日期），EXIF 场景日期由图片给，只该借它的"地名→路径" → 改判 `cr.path`

第 3 个最阴：**静默失败**，日志里什么都不打。

## 八、下周探索（可选，不阻塞）

### 8.1 先做判定实验

用**确定带 GPS** 的样本（`frame0010760.jpg`）走 QQ 原图通道，看落盘文件有没有 `34853`：

| 结果 | 含义 | 下一步 |
|---|---|---|
| 有 GPS | 通道可抢救地点 | 把"取原图"做成常驻能力 |
| 无 GPS，时间在 | 服务端剥 GPS | 地点只能口述，终止探索 |
| 连时间都没有 | 原图档没取对 | 复查取图路径 |

### 8.2 待验证：苹果设备

iPhone 默认写 GPS（相机「位置信息」开关默认开），但**经 QQ 传输后是否保留**尚未实测。
判定方法同 8.1。**不需要专门借设备**——判定逻辑已兼容"有则用、无则问"，测不测都不影响架构。

### 8.3 若要做：协议端形态对比

| 协议端 | 形态 | 原图可达性 | 已知问题 |
|---|---|---|---|
| NapCat | Docker / 原生注入 | `/get_image` 返回 `Ori/` 路径，可达 | macOS 注入版 `dyld missing symbol`；Docker 版依赖 colima，90 上下载镜像超时 |
| Lagrange.Core | .NET 单文件 | 待验证 | 需签名服务器 |
| SnowLuma | TypeScript，QQ → OneBot v11 | 待验证 | 多个同名仓库，选型需谨慎 |
| icqq / oicq | Node 库 | 大概率不可达 | 协议过时 |

**对比维度**不是"能不能跑起来"，是四条：原图路径能否被 bridge 直接读到 / 是否支持按 md5 取原图 / 是否保留完整 EXIF 段 / 登录稳定性。

**注意**：搬到 90 不等于自动解决——看形态不看位置。原生进程直接可读；容器要挂载卷；跨机必须中转。

## 十、关键决策与口径

| 决策 | 理由 |
|---|---|
| 用 QQ 不用微信 | 微信个人号封号风险高；QQ 协议端生态存续久 |
| 本地 Qwen3.5-Q4KM | 对话不出机器，零外部依赖 |
| 事件摘要而非文件名喂模型 | 文件名说不了话，摘要才能"记得" |
| 目录是真相，EXIF 是派生 | QQ 传图必丢元数据，文件名和目录才可靠 |
| scope_id 用完整路径 | 搜索"深圳"能前缀命中它下面的区 |
| 不伪造 GPS | 假坐标会让"可验证"变成"不可信" |
| 哥哥弟弟是两个人 | 大号小号是同一个人的模拟，但人设里必须是两个人 |

### 给 PPT 的口径

> 拍摄时间可通过「勾选原图 + 协议端取原图档」自动获取；
> 地理坐标取决于源图是否携带 GPS，**华为实测不可得**；
> 有 GPS 的图全自动入册，没有的走追问——**地点默认靠口述，这是终态**。

### 一个必须如实写的局限

**本地 Qwen（qwen35-4b-q4km）理解力明显弱于 DS API**，是体量差距。

现在的"温度"是靠**话术模板 + 强约束**撑起来的，不是模型自己聪明：

- 说话人信息放在 prompt **最末尾**（4B 对开头注意力弱）
- 角色卡把易错点写死（"以这一条消息的号码为准"）
- 追问话术给**完整例句**，不让它自由发挥
- 上下文 2048 → 8192（每槽）

**PPT 里别说成"模型很懂人"。**
