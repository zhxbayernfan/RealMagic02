# Jetson AGX Orin(192.168.1.123) 部署 Sentrix Home Web 管线运行分析

## 1. 设备规格

| 项目 | 123 (Orin) | 200 (对比基准) |
|----|----|----|
| 型号 | NVIDIA Jetson AGX Orin Developer Kit | 台式机(单RTX 3090) |
| CPU | 12核 ARM aarch64 | Intel/AMD x86_64 |
| GPU | 32核 Ampere(集成, 共享内存) | RTX 3090 24GB GDDR6X(独立) |
| 内存 | 64GB LPDDR5(与GPU共享) | 128GB DDR4(独立于GPU) |
| 存储 | eMMC 54G(剩5.9G, 使用率89%) | NVMe SSD(余量充足) |
| OS | Ubuntu 22.04 aarch64 / JetPack R36.4.7 | Ubuntu 22.04 x86_64 |
| 功耗模式 | MAXN(档位0, nvpmodel -q已确认) | N/A |

**核心差异**：Orin是嵌入式SoC，GPU与CPU共享内存/总线，无独立显存；存储为eMMC而非NVMe。这两点直接导致后续管线瓶颈。

## 2. 管线运行结果

### 2.1 周四(08/27)：全流程跑通

测试视频：3分钟聚餐视频(19MB, HEVC编码, 1280x782)

| 阶段 | 耗时 | 结果 |
|----|----|----|
| ffprobe读取元数据 + GPS反解 | ~2s | ✓ |
| ffmpeg HEVC→h264预览转码 | ~120s | ✓ |
| WorldMM关键帧提取 | ~240s | ✓ (33场景/54关键帧) |
| VLM描述(ollama gemma4:e2b本地推理) | ~4440s | ✓ (54/54全部成功) |
| 场景summarize事件聚类 | ~120s | ✓ |
| **管线总耗时** | **约4580s(76分钟)** | **✓ 全流程通过** |

### 2.2 周五(08/28)：环境异常导致页面无结果

周五重新部署时遇到以下问题，导致前端无数据展示：

1. VLM模型丢失(ollama进程退出后未自动重载)
2. 后端线程池耗尽(ffmpeg转码阻塞任务调度)
3. 磁盘空间不足(eMMC剩余5.9G)

已修复：切换VLM至本地ollama + 禁用ffmpeg预览转码 + 清理衍生文件。

**当前状态**：环境已恢复，待重新导入视频后可再次跑通管线。

## 3. 性能对比与瓶颈分析

### 3.1 同视频耗时对比

| 指标 | 200(RTX 3090) | 123(Jetson AGX Orin) | 倍率 |
|----|----|----|----|
| 预览转码 | <5s | ~120s | ~24x |
| WorldMM提取 | ~3s | ~240s | ~80x |
| VLM描述(54帧) | ~263s | ~4440s | ~17x |
| **管线总耗时** | **~266s(4分27秒)** | **~4580s(76分钟)** | **~17x** |
| 关键帧成功率 | 54/54(100%) | 54/54(100%) | — |

### 3.2 瓶颈占比(以123全流程4580s为基准)

| 阶段 | 耗时 | 占比 | 根因 |
|----|----|----|----|
| VLM推理 | 4440s | 96.9% | 单帧82s，54帧串行推理 |
| WorldMM提取 | 240s | 5.2% | ARM架构下OpenCV/ffmpeg效率低 |
| 预览转码 | 120s | 2.6% | ffmpeg使用CPU软编码，未启用NVENC硬件转码(实测`h264_nvenc`/`hevc_nvenc`在列，可用) |
| — | 4800s | — | — |

> 注：阶段耗时合计4800s高于管线总耗时4580s，因部分阶段存在并行重叠，各阶段占比=该阶段耗时÷总耗时4580s，合计>100%属正常。

### 3.3 关键发现

**VLM推理占总耗时96.9%，是主矛盾**。只优化VLM即可将全流程从76分钟压到约20-25分钟，无需动硬件。

## 4. 优化方案(优先级排序)

### P0：先止血(可靠性)

| 项 | 现状 | 方案 | 收益 |
|----|----|----|----|
| systemd托管 | 手工启停，崩溃不重启 | `Restart=always` + `RestartSec=10` | 崩溃10秒自恢复 |
| 磁盘监控 | 剩5.9G无告警 | df阈值(<15%告警/<8%清理) + 衍生文件自动清理 | 防止写入失败 |
| 模型资产幂等 | 丢失后靠人发现 | 启动时校验+自动pull，模型文件独立目录管理 | 消灭40分钟重pull |

### P1：打掉三个瓶颈

| 瓶颈 | 现状 | 方案 | 预估收益 | 风险 |
|----|----|----|----|----|
| 预览转码 ~120s | ffmpeg CPU软编码(实测`h264_nvenc`/`hevc_nvenc`在列，可用) | 启用硬件转码 `ffmpeg -c:v h264_nvenc`，或浏览器Chrome 120+已支持HEVC软解跳过转码 | 省~120s | 需实测验证硬件转码速度 |
| WorldMM提取 ~240s | 单线程慢80倍 | 检查OpenCV是否ARM SIMD优化版+开多线程；不行换ffmpeg+scenedetect轻量抽帧 | 80倍差距异常，大概率没开并行 | 需实测验证 |
| VLM推理 ~4440s(占97%) | gemma4:e2b FP16，单帧82s | ①INT4量化(7.2G→2-3G，顺带解磁盘)；②2-4路并行推理(64G内存够用) | **下阶段目标：全流程降至20-25min** | 并行非线缩放(共享GPU)；ollama对gemma4:e2b的INT4支持需验证，不支持则换llama.cpp |

> **注意**：并行推理不能线性缩放——32核Ampere是共享的，2-4路并行会抢同一GPU，"压到1/4"需要实测验证，此处为理论预估。INT4量化需确认ollama是否支持gemma4:e2b的4bit量化，不支持则需换用llama.cpp框架。

### P2：架构长期项

- **计算与展示分离**：200跑重管线 → 产物(SQLite + 缩略图)同步到Orin做展示。Orin定位为端侧看板 + 轻量qa推理。
- **环境容器化**：用JetPack container锁版本，部署从"手工配"变"一条命令"。
- **存储外挂NVMe/USB3.0 SSD**：eMMC 89%是硬瓶颈，Orin支持M.2 Key M和USB3.0，模型+视频迁到外接SSD比一切优化都实在。
- **断点续传**：关键帧已提但VLM失败的帧单独重试，不做全量重跑。

---

## 5. 交差总结(三句话)

1. **成果**：Orin端到端跑通全流程，关键帧54/54成功率100%，场景聚类输出正常。
2. **数据**：全流程76min，瓶颈高度集中——VLM推理占96.9%(4440s)、WorldMM提取占5.2%(240s)，预览转码(120s)周五已禁用。
3. **方案**：重管线放200、Orin做端侧展示；VLM量化+并行后下阶段验收目标降至20-25min，不动硬件。
