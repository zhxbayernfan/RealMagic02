# Ollama与TensorRT对比(Jetson Orin端侧VLM场景)

> **通俗理解**:已有照片是**教材**,照片的文字描述是**老师用语言授课**,不同模型是**不同的学生**,QA集是组里钻研出的**满分考题**——我们做的事情,就是**搭建一个更好的考场**,让学生考出更高的分数,做出更好的回答.

## 1. 定位差异

| 项 | Ollama | TensorRT(Edge-LLM) |
|---|---|---|
| 本质 | 本地模型运行管理器(llama.cpp后端) | NVIDIA官方推理优化引擎 |
| 模型格式 | GGUF(FP16/Q8/Q4等通用量化) | 编译后的engine文件(针对具体GPU架构) |
| 获取方式 | ollama pull一行命令,即拉即用 | 源码/配方编译,build后部署 |
| API形态 | OpenAI兼容/v1/chat/completions | 自带server(OpenAI兼容程度视实现) |
| 目标用户 | 个人开发者/快速原型 | 生产环境/性能敏感场景 |
| Jetson支持 | 社区级(非一等公民) | 官方(JetPack/CUDA版本矩阵配套) |

一句话:Ollama是"傻瓜相机",构筑好就能开始评测photobench,但是遇到问题容易卡脚;TensorRT是"专业摄像棚",构筑复杂但是架设好了之后更容易跑通管线.

## 2. 推理机制对比(思考模式/输出路径)

### 2.1 两条输出路径

```
Ollama路径:
  prompt → 模型内部reasoning(思考过程) → content(正式回答)
           ↑ 思考与content共用同一个输出预算(num_predict)

TensorRT路径:
  prompt → content(直接输出)
           ↑ 部署时即无reasoning路径,输出即结果
```

### 2.2 Ollama的思考模式问题(管线失败根因)

- 现代思考型模型(如gemma系)在chat接口下,会先输出一段reasoning再输出正式content
- Ollama对思考模式**没有统一的剥离/关闭开关**——是否思考、思考多长,由模型模板决定,调用方不可控
- 管线设置num_predict=2048时,思考过程消耗1500+ tokens,预算耗尽,content返回**空字符串**
- 下游管线拿到空描述→Agent无法检索照片→全链路失效
- 这不是参数调优能解决的:即使加大预算,思考内容混入/挤占输出的问题依旧存在,且耗时不可控

> 用考场比喻:不是学生不会答题——是100人大教室太吵,学生光打草稿应付噪音,铃响了**答题卡还是白的**.

### 2.3 TensorRT的输出可控性

- 部署时模型即按"纯content输出"构建,无思考分支
- 每次推理的全部预算都花在正式内容上,caption JSON生成稳定
- 对管线场景:调用方拿到的就是可直接解析的结构化输出,不需要后处理剥离思考内容

## 3. 量化与性能

| 项 | Ollama(GGUF) | TensorRT(INT4+MTP) |
|---|---|---|
| 量化方式 | GGUF通用量化(与硬件无关) | INT4权重量化+NVIDIA深度优化 |
| 推理加速 | llama.cpp通用kernel | 算子融合+定制kernel |
| 推测解码 | 无 | MTP多token预测(draft模型草拟,大模型验证) |
| 典型显存 | FP16约8GB级 | INT4约3GB级 |
| 性能量级 | 通用水平 | 同模型典型提升2-3倍 |

显存项对Jetson尤其关键:AGX Orin的64GB LPDDR5是CPU/GPU**共享内存**,VLM显存占用每降1GB,系统可用内存就多1GB,直接减少swap/OOM风险.

## 4. 部署与维护

| 维度 | Ollama | TensorRT |
|---|---|---|
| 首次部署 | 低(pull即用) | 高(编译engine,依赖版本矩阵锁定) |
| 版本依赖 | 弱(自带运行时) | 强(JetPack/CUDA/TensorRT三者必须匹配) |
| 升级模型 | 重pull即可 | 重新编译engine |
| 调试透明度 | 黑盒(社区项目) | 可配置(量化参数/draft参数可见可调) |
| 出问题后的恢复 | 重pull/重启服务 | 重新build engine(有配方则快) |

部署成本是TensorRT的主要代价:engine编译一次绑死一套硬件+软件版本,换版本就要重编译.但换来的是:所有性能参数显式可控,排障时能精确到配置项,而不是猜Ollama内部行为.

## 5. 端侧(VLM/Agent管线)场景适配性

管线结构:photo_import → VLM生成caption(JSON) → FTS索引 → Agent检索 → QA评测.

| 管线需求 | Ollama表现 | TensorRT表现 |
|---|---|---|
| caption稳定产出(JSON) | 思考挤占预算,content空,管线中断 | 纯content,JSON可直接解析 |
| 输出长度可控 | num_predict被思考稀释 | 预算全给正式输出 |
| 显存压力(共享内存) | 8GB级FP16,挤占系统内存 | 3GB级INT4,余量充足 |
| 批量图处理耗时 | 通用性能 | MTP推测解码,批处理更快 |
| Agent工具调用 | content空导致0步无调用 | content正常,tool call可解析 |

适配性结论:VLM/Agent管线对推理引擎的**核心要求是输出可控**——每一张图的caption都必须是可解析的结构化内容.这条Ollama结构性不满足(思考模式不可关),TensorRT天然满足(无思考路径).量化与速度是加分项,输出可控性才是选型的决定因素.

注:TensorRT路线也有自身工程量——engine编译、多模态模型配方适配、管线联调,并非银弹,部署阶段同样需要踩坑.

## 6. 小结

| 决策维度 | 更优方 | 说明 |
|---|---|---|
| 快速原型/临时验证 | Ollama | 部署成本几乎为零 |
| 管线生产/稳定输出 | TensorRT | 输出路径可控是硬性要求 |
| 显存受限(共享内存) | TensorRT | INT4节省约60%显存 |
| 批量处理性能 | TensorRT | MTP+定制kernel |
| 维护成本 | Ollama | 无编译,升级无感 |

**结论**:端侧VLM/Agent管线场景下,推理引擎选型的决定性因素是**输出可控性**而非单纯的推理速度.Ollama因思考模式不可关,在管线场景存在结构性缺陷;TensorRT Edge-LLM以更高的部署成本换来输出稳定、显存减半、批量加速,是Orin端侧管线生产的合理选型.两条路线可共存:Ollama用于日常模型验证,TensorRT用于管线生产部署.

> 回到考场比喻:教材没换、学生没换、考题没换——**换的是考场**.给考生一间安静的20人包间,分数自然往上走.
